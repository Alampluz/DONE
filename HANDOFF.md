## Build & deploy loop
Deploys are automatic. Push a changed file under `src/` to `main` and `.github/workflows/ci.yml` does the rest: `build.sh` concatenates the six parts and injects the Supabase URL + anon key, every inline `<script>` is syntax-checked, `run_tests.sh` runs every suite in `tests/`, and only then is the built `index.html` committed to the repo root by `github-actions[bot]`. A failing suite blocks the deploy instead of shipping with it.

```bash
./build.sh          # writes app/index.html (override SUPABASE_URL / SUPABASE_ANON to point elsewhere)
./run_tests.sh      # all 27 against that build
# then upload the changed src/ file(s) via github.com/Alampluz/done/upload/main/src
```
`app/` is gitignored — the repo holds `src/`, `tests/`, the runners and the built root `index.html`, nothing else. Never edit `index.html` in the repo by hand; CI overwrites it from `src/` on the next push, and the bundle carries a comment saying so.

GitHub Pages sits behind a CDN — after each deploy users need a **hard refresh** (Ctrl/Cmd+Shift+R).

Uploading through the GitHub web UI: the commit fires before large batches finish uploading, so files go missing silently — upload in batches of ~10, wait, commit, then check the tree via the contents API and re-upload whatever did not land. GitHub's "Processing your files…" step can also stall for 10+ minutes and then land every queued manifest at once (4 Sep: three commits in 20 s) — do not re-upload while it is stalled, it only multiplies the commits. CI copes: the publish step rebases onto the moved `main` and retries the push (4 Sep) after one run failed exactly that way. The linked Chrome window reports a 0×0 viewport, so ref/coordinate clicks do nothing; submit the form with a scripted `click()` on the Commit button.

## Testing
**Run them with `./run_tests.sh` (or `run_tests.ps1` on Windows).** It copies `app/index.html` into a scratch dir, installs `jsdom` there if needed, runs every suite and exits non-zero on any failure — so it can gate a deploy once CI exists.

`run_tests.sh` now exports `NODE_PATH="$run/node_modules"` (fixed 31 Aug). Without it every suite failed with MODULE_NOT_FOUND even though jsdom was installed: node resolves `require('jsdom')` from the **suite file's** directory (`tests/`), not from the working directory, so a scratch-dir install is invisible to it. A clean PASS=0 FAIL=27 is that bug, not a broken app. `run_tests.ps1` got the same fix (`$env:NODE_PATH`), but has not been re-run on Windows since.

43 suites in `tests/`: attach, auto, bigboard, board, boardact, boardreport, bulk2, calendar, cmtdel, csv, customauto, dates, email, filter, forgot, formula, guard, history, linkmirror, listpaste, membersearch, mention, ownerheart, paging, presets, profile, quickfilters, report, reqempty, reqhist, resetlink, rowmenu, signoff, signupconfirm, sla, sprintE, throughput, viewpicker, vis, ws, selects, wsorder, corefields.

Each suite does `fs.readFileSync('index.html')` — a **relative** path — so they only run from a directory holding the built `index.html` *and* resolving `jsdom`. Run them any other way and all 27 fail on MODULE_NOT_FOUND or ENOENT, which reads exactly like a broken app. That is what `run_tests.sh` is for.

Gotchas: jsdom outside-only mode doesn't run inline `onclick` (call the function directly); mock supabase query chains need `neq/not/is/or/gte/lte/gt/lt/in` — every suite carries its own copy-pasted mock, so a chain method newly used in app code has to be added to whichever mocks reach that code path. `test_membersearch` and `test_dates` locate code by **comment text** — renaming a comment can break a suite that has nothing to do with the change.

## Dates (30 Aug)
One format everywhere: **`31 Aug 2026`** — `DATE_FMT` in part2 drives `fmtDate`, `fmtDateTime` and `tvFmtDate` (part3). Both date functions previously hid the year whenever it matched the current year, which read as "3 Sept" on a board spanning a year end. The year is now always shown. `tvFmtDate` parses `yyyy-mm-dd` as `T00:00:00` local so a bare date never slips a day on a UTC+7 clock, and both return `''` rather than `Invalid Date` for junk. Covered by `tests/test_dates.cjs`.

## Teams (30 Aug)
`teams` + `team_members`, admin-managed in **Admin → Teams**. A team is a saved group of people and **nothing else — no policy anywhere references a team**. Picking one in a member dialog ticks its people; access is still stored per person in `workspace_members` / `project_members`. So adding someone to a team later does NOT give them access to anything, and deleting a team takes nothing away. That was a deliberate call (static bulk-add, not a dynamic grant) — if it ever needs to become a real grant, that is an RLS change, not a UI one.

`teamAddHTML()` / `wireTeamAdd()` in part2 are shared by both member dialogs; team names ride along inside `searchKey`, which is why one box searches "name, team, role, or email". `wireTeamAdd` skips disabled boxes and reports them ("3 can't be added here") rather than silently under-ticking. Admin → Users gained a **Teams** column. Unique index on `(company_id, lower(name))`, surfaced as "There is already a team called X".

## Ownership — boards and workspaces (30–31 Aug)
Every board and workspace has **one or more owners** (`project_owners` / `workspace_owners`).

- **Workspace owner** — everything inside the workspace: rename, description, colour, members, and every board in it (settings, columns, groups, and deleting the board). **Not** deleting the workspace.
- **Board owner** — that board's settings, columns, groups, sign-off, delete.
- **Admin** — all of the above, plus deleting a workspace.

Deleting a workspace destroys every board and task inside it, which is why it is the one thing an owner cannot do (`workspaces_delete` is `is_admin()`, and `canDeleteWs()` mirrors it in the UI). `can_manage_board()` reaches the board's owner *and* the owner of the workspace it sits in — see `migrations/2026-08-30d_ws_owner_scope.sql`.

Task create/edit/assign is untouched — that still runs off `canEdit()`. **Do not reuse `canEdit()` for settings**; it means "can work on tasks".

**Where owners are set and shown:** Edit board and Edit workspace both show the owners with a **Manage owners** button that jumps to the right dialog; Admin → Workspaces lists the owner under each name. `keep_one_owner` is a DEFERRABLE CONSTRAINT TRIGGER — it must not fire on the cascade when the parent itself is being deleted, a bug that blocked Delete workspace entirely — and admins override it, with the UI confirming before anything is left ownerless.

UI: a **heart** marks the owners in **Board members** and **Members of ‹workspace›** — outline ♡ = not an owner, filled ♥ (`#C0392B`) = owner. Clicking toggles both ways. Both states stay clickable so the control reads as a toggle rather than an add-only button; without permission neither is clickable and the title says why. `ownerHeartHTML()` in part2, covered by `tests/test_ownerheart.cjs`.

Built for ~250 staff: each role group lists **current members first**, then alphabetical, with a `· 3 of 180` count on the heading and a live `N of 250 people on this workspace` line under the search. The "Always has access" strip caps at 4 names + "and N more". Measured at 250 rows in jsdom (no layout, so a pessimistic floor): 59 ms to build, worst keystroke 15 ms — the filter is not the constraint at this headcount.

Both member dialogs open with a **search box** (`searchBoxHTML` / `searchKey` / `wireMemberSearch` in part2): type a name, email, job title or role and the list filters live, with empty role headings folding away. Rows opt in with `data-search`, role headings with `data-group`. Covered by `tests/test_membersearch.cjs`.

Board members opens with a **People on this board** list (owners first) built from owners + workspace members + admin/management + partner members; the partner checkboxes below are unchanged. Owner lists load in `refreshCore` as `S.boardOwners` / `S.wsOwners`; read them through `boardOwnerIds()` / `wsOwnerIds()`, never off the project row — there is no `owner_id` column any more.

## Security — RPC surface (30 Aug)
9 SECURITY DEFINER functions were executable by `anon` over `/rest/v1/rpc/<name>`. Public request forms are on, so `anon` is a live, reachable role. The worst was `auto_notify()` — it inserts a notification row for any `user_id` with attacker-chosen title and body. `recompute_open_slas()` and `restore_deleted_task()` were exposed too but already carry `is_admin()` / `is_staff()` guards internally.

Fixed by `migrations/2026-08-30_lock_down_internal_rpc.sql`. The trap: EXECUTE was held by **PUBLIC** (the `=X/postgres` ACL entry), not granted to `anon`/`authenticated`, so `revoke ... from anon, authenticated` succeeds and changes nothing. Revoke from `PUBLIC`, then grant back to `authenticated` only where the UI calls it. Verify with `has_function_privilege('anon', oid, 'EXECUTE')`, not by reading the migration.

Safe because every internal caller runs as the owner: the six trigger functions that call these helpers are all SECURITY DEFINER, pg_cron runs as postgres, and `service_role` keeps its explicit grant. Verified after applying — `run_automation_sweep()` still completes the full chain.

The only `rpc()` calls in `src/` are `run_automation_sweep`, `restore_deleted_task` and `recompute_open_slas`.

## Database notes
- Helper fns (SECURITY DEFINER, avoid RLS recursion): `my_company()`, `is_admin()`, `is_staff()`, `is_ws_member()`, `is_board_member()`, `req_type_visible()`, `has_project_access()`, `is_board_owner()`, `is_ws_owner()`, `can_manage_board()`, `can_manage_ws()`, `board_preset()`, `can_write_board()`, `can_edit_task()`, `can_edit_task_id()`.
- Notifications `kind` values: assigned, review, request, sla_warning, sla_breach, overdue, mention, automation, approval, approval_decided.
- Hard-learned RLS gotchas: INSERT..RETURNING evaluates the SELECT policy before self-lookup helpers can see the row; cross-table subqueries inlined in policies cause infinite recursion (wrap in definer fns); CHECK constraints must be widened alongside RLS.
- Storage bucket `attachments`; storage objects must be deleted via the Storage API, not SQL.
- **RLS cost on big tables (6 Sep):** `tasks_select` used `has_project_access(project_id)` per row — 3,000+ definer-function calls per page, ~780 ms. Rewritten as `project_id in (select id from projects where has_project_access(id))` (hashed subplan, ~125 ms; `migrations/2026-09-06_tasks_select_policy_per_project.sql`). Same shape is worth applying to `subtasks`/`comments`/`task_checklist` policies if they ever get slow.
- **Bulk writes without notification storms:** `alter table tasks disable trigger user` inside the transaction (table owner may; `session_replication_role` needs superuser and the MCP role is not one). Re-enable in the same block. Used by the monday import.
- **Getting a large file into the database from a Cowork session:** neither the cloud container nor the device shell reaches supabase.co, and pushing megabytes through SQL text is prohibitively expensive. Route that worked: open the live app in the linked Chrome (April's session), inject an `<input type=file>`, `file_upload` the staged file onto it, and let page JS `upsert` in batches into a staging table with an admin-only RLS policy. The data never passes through the conversation.
